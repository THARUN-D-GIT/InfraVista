## 1. Summary

P3 implemented the indicator computation and spatial aggregation pipeline for the InfraVista pilot zones HSR and Whitefield.

The pipeline reads the P2 published GeoJSON package, validates its layer metadata, projects the input geometries to the configured processing CRS, computes infrastructure indicators at grid and study-window levels, and generates GeoJSON outputs and a run manifest.

The completed run produced:

- 3,618 grid-level indicator records in the latest corrected run (`20261106T191045Z_indicators`).
- 36 study-window-level indicator records.
- 20 grid-level indicator types in the latest corrected run (`20261106T191045Z_indicators`).
- Outputs for both HSR and Whitefield.

## 3. Configuration and assumptions

Configuration file:

`config/indicators.yml`

| Setting | Value |
|---|---|

| Processing CRS | EPSG:32643 |
| CRS approval status | Proposed, not approved |
| Boundary version | boundary_pilot_v1 |

| Grid cell size | 500 metres |
| Minimum coverage for density | 0.25 |

The two pilot zones use the configured HSR and Whitefield centre coordinates.

The study windows are circular 2.5 km radius areas. They are not official administrative boundaries.

Road classes are grouped into:
- Motorised network
- Service and track
- Pedestrian and cycle
- Not existing
- Other unmapped class

Construction and proposed roads are retained separately and are not treated as existing infrastructure.
### Road-class and road-node handling

The following road groups are the current P3 proposed classification, configured in `config/indicators.yml`. They remain subject to P1 approval:

| Group | OSM `highway` values |
|---|---|
| `motorised_network` | `motorway`, `motorway_link`, `trunk`, `trunk_link`, `primary`, `primary_link`, `secondary`, `secondary_link`, `tertiary`, `tertiary_link`, `unclassified`, `residential`, `living_street` |
| `service_and_track` | `service`, `track` |
| `pedestrian_cycle` | `footway`, `path`, `steps`, `cycleway`, `pedestrian` |
| `not_existing` | `construction`, `proposed` |
| `other_unmapped_class` | Any other `highway` value not listed above |

Unknown highway values are retained in `other_unmapped_class`, rather than dropped or silently included in the motorised network. In the current Whitefield input, this includes one `corridor` feature and one `road` feature (2 of 3,107 road features). These remain separately reported pending review.

The published input package also contains `road_nodes_hsr` and `road_nodes_whitefield`. These are tagged OSM point features (such as crossings, street lamps, bus stops and traffic signals), not validated road-network topology. P3 therefore excludes them from the current road-density and network-connectivity calculations. Their possible use in future point-based transport or amenity indicators is outside the current P3 scope.

Facility point/polygon deduplication uses a 25-metre tolerance for selected facility categories. This is a documented processing assumption, not an independently approved rule.

## 4. Implemented indicators

Indicators are computed at both grid-cell and study-window levels.

## 8. Known limitations and pending decisions

1. OSM completeness has not been independently verified.
2. Missing mapped features must not be interpreted as confirmed absence of infrastructure.
3. EPSG:32643 is proposed and requires approval.
4. The 25-metre facility deduplication tolerance requires review and approval.
5. ODbL attribution and share-alike obligations require review. Rights status remains `review_required`; do not treat the outputs as approved for unrestricted publication.
6. Road centreline length is not lane-kilometres.
7. Storm drains may be incompletely represented in OSM.
8. The 2.5 km study windows are pilot analysis windows, not official administrative boundaries.
9. Independent P6 validation is pending.
10. The original normalized GeoPackage ZIP referenced by the P2 handoff was unavailable; P3 used the later published GeoJSON package.
11. Whitefield contains two road features with highway values not included in the configured groups (`corridor`: 1; `road`: 1). They are retained under `other_unmapped_class` pending classification review.
12. The published `road_nodes` layers contain tagged OSM point features, not validated road-network topology. They are excluded from current P3 road-density and network-connectivity calculations.
13. Facility polygon-to-polygon deduplication is not implemented. Inspection of the original published GeoJSON found two same-category college polygon pairs with complete overlap of the smaller polygon: HSR (`relation/1804672`, RJS Polytechnic, 16.48 m²; and `way/967216468`, 311.63 m²) and Whitefield (`relation/1969878`, Vydehi Medical College Building, 9,777.05 m²; and `way/494678981`, 207,767.76 m²). All four geometries are valid Polygons. The intersection area equals the smaller polygon area in each pair, while the polygons are not identical; their boundary intersection length is 0 m. The Whitefield relation is contained within the larger way. The HSR relation is fully covered by the larger way by area, although the strict `within` predicate returned false. These may represent nested campus/building features or duplicate representations; source properties and geometry alone do not establish institution identity. Both features in each pair are retained in current counts pending P1/P6 review; facility totals should not be interpreted as confirmed unique institutions.

Quality flags are retained in the generated outputs to communicate relevant limitations, including incomplete source coverage, partial grid-cell coverage, small denominators and deduplication assumptions.
